## 2. ⭐⭐⭐ ARC-AGI-3 的 99.9%:外殼換掉,分數差 37 個百分點

這是本次發布最出圈、也最容易被誤讀的數字。

| 外殼 | 分數 | 花費 |
|---|---|---|
| **ARC Prize 的 Standard harness**(受控) | **62.7%** | 約 **$26K** |
| **OpenAI 自己的 Provider Adapter** | **99.9%** | 約 **$19K** |

**兩個外殼的差別在哪(這才是重點):**

```mermaid
flowchart LR
    subgraph Std["Standard harness"]
        S1["只能在請求之間<br/>帶可見的筆記"]
    end
    subgraph PA["OpenAI Provider Adapter"]
        P1["保留不透明的<br/>推理狀態"]
        P2["自動壓縮長對話"]
        P1 --- P2
    end
    Std -->|"62.7%<br/>約 26K 美元"| R1["同一個模型"]
    PA -->|"99.9%<br/>約 19K 美元"| R1
```

> ⭐ **Provider Adapter 讓模型能重複使用更多先前的工作** ——
> 在 167 組共享的 game-reasoning 配對上,**快 3.66 倍、少用 49% 的 token**。
> **ARC Prize 自己的解讀就是:這個落差主要來自外殼。**

⭐ **同場加映的對照(讓 62.7% 的份量顯出來):**
同樣用 Standard harness,**Claude Opus 5 是 30.2%、GPT-5.6 Sol 只有 7.8%** ——
**62.7% 依然是全場第一,而且是斷層式的第一。**

> ⚠️ **所以正確的說法是:**
> 「Astra 在受控外殼下把 ARC-AGI-3 的紀錄從 30% 推到 62.7%」是真的、而且很了不起;
> 「Astra 打穿了 ARC-AGI-3」則需要加上「在 OpenAI 自製外殼下」這個括號。

### ⚠️ Caleb 補的一個容易搞混的對照:NVIDIA 的「100%」

有人會問:NVIDIA 不是前陣子也在 ARC-AGI-3 拿了 100% 嗎?

| | NVIDIA | GPT-6 Astra |
|---|---|---|
| **資料集** | **public**(公開,大家都看得到) | **semi-private**(環境由 ARC Foundation 隱藏並代管) |
| **做法** | **AVO** —— 一層給 **Opus 5** 用的 agentic harness(持久記憶、上下文管理、執行環境) | 模型本身 + 兩種外殼 |

> ⭐ 兩者**不可直接比較**。順帶一提,semi-private 因為要對外呼叫 lab 的 API,
> **仍有資料外洩的可能性,環境有機會被摸清楚** —— 只有 fully private 才是完全隔離。

### ⭐ 補充:ARC-AGI-3 實際上長什麼樣(跟宣傳圖不一樣)

它看起來像一堆漂亮的小遊戲,但**模型收到的不是截圖也不是影片**:

> 評測方送來的是一個 **64×64 的文字網格**,每格是 16 色之一,**以 JSON 物件送給模型**;
> 模型回傳 action token,環境再把更新後的網格送回來。

## 4. ⭐⭐ 這代真正的主角:computer use

| | Astra | Sol |
|---|---|---|
| **OSWorld 2.0** | 72.6% | 65.7% |
| **平均完成時間** | **40 分鐘** | 75 分鐘 |
| **Mind2Web(配新版 Codex 外殼)** | **速度 1.9×** | — |

官方演示的範圍很直白:**KiCad 畫 PCB、Excel 打競賽、填美國稅表 1040、前端 QA、Power BI、瀏覽器、Unity、Blender、Jupyter** ——
**凡是有按鈕、有介面的軟體,它現在都能直接上手。**

### ⭐ 早期實測(對工程師最有參考價值的兩則)

- **改 CRM 的節點式工作流**:讓 Codex 裡的 Astra 直接操作 Chrome,加節點、改提示詞、重新連線,**全程沒動手** ——
  而這件事測試者自己之前**折騰一小時沒搞定**。
- ⭐⭐ **拿它當 QA 用**:在預覽分支上回歸測試剛修完的**串流競態條件** ——
  自己開頁面、逐個點擊、盯 console 報錯、刷新復現,**一跑就是 1 小時 45 分鐘**,還順手修了幾個問題。
  > 測試者原話:**「如果你還沒用瀏覽器操作做 QA,趕緊試。」**

⚠️ **但也要看反面意見。** Caleb 的體感相反:
> **「我個人用 agentic computer use 的經驗大體上是令人失望的 —— 這是我很想要它成真、但我們還沒到那裡的東西之一。」**
> 他承認 Astra 的分數「確實在暗示我們快要有家用 Jarvis 了」,**但那是「快要」,不是「已經」。**

> ⭐ **這兩種說法可以並存**:官方演示與早期權限測試者跑的是**挑過的任務**,
> 一般使用者遇到的是**沒挑過的任務**。**自己的評測集才算數。**

## 5. ⭐⭐⭐ Token 效率 ≠ 成本效率,而且它正在改變產業的張力

這是 Caleb 那支影片最有原創性的一段。

| 維度 | Astra 的表現 |
|---|---|
| **成本效率(每 token 多少錢)** | ❌ **很差** —— $10/$50,而 Sol 短上下文只要 $4/$20 |
| **Token 效率(完成同樣工作要幾個 token)** | ✅ **很好** —— DeepSWE 上只用 Sol 一半的輸出 token;AA 的複合基準裡**用最少 token 完成工作** |

⭐ **結果是:兩者的 Pareto frontier 幾乎重疊** —— 單價貴很多,但因為省 token,實際成本沒差多少。
在編程任務上甚至**反而便宜一半**(§3.2)。

### 這對產業意味著什麼(值得單獨記)

```mermaid
flowchart TB
    A["模型越來越 token 有效率"] --> B["每個 token 交付的智能變多"]
    B --> C{"OpenAI 怎麼處理<br/>這個效率紅利?"}
    C -->|"選項一"| D["降價<br/>讓使用者的每任務成本下降"]
    C -->|"選項二"| E["提高單價<br/>把紅利留成毛利"]
    E -.->|"從 Astra 的定價看<br/>目前走的是這條"| F["⚠️ 效率紅利<br/>先進了 OpenAI 的口袋"]
```

> ⭐⭐ **張力在哪:對一個靠 token 變現的 lab 來說,模型越省 token,
> 同樣的價值需要的計費 token 就越少 —— 也就是同樣的需求只需要更少的推論算力。**
>
> 而從 Astra 的定價看,**這個效率紅利目前是留成毛利,而不是回饋成更低的每任務成本**
> (⚠️ 前提是 Astra 的推論成本本身沒有暴增太多 —— 這點外部無法驗證)。

⭐ **對其他實驗室的意涵更狠:**
> 「追上 OpenAI 不只是追能力,**更是要用更少的工作量達到同樣的能力**。」
> DeepSWE 上 Gemini 3.8 Flash 與 Opus 5 分數與 Astra 接近,
> **但每 token 的營運效率差了 4–5 倍。**

## 6. ⚠️⚠️ 安全:第一個「Critical」等級,以及一個令人不安的細節

**Astra 是 OpenAI 準備度框架(Preparedness Framework)下第一個達到網路安全 Critical 等級的模型。**

**Critical 的定義(官方口徑):**
> 能在**多個經過強化的真實關鍵系統**上,**無需人類逐步指導**就找出並開發出可運作的各級別零日漏洞利用;
> 或僅給一個高階目標,就能自行設計並執行端到端的新型攻擊策略。

📌 核實到的具體證據:在一個**由 2026 年 6–8 月揭露的 20 個高危 V8 漏洞**組成的內部基準上,
Astra 的任意程式碼執行率遠高於 Sol,**並且在評測過程中發現了兩個先前未知的零日漏洞。**

### ✅ 好消息:安全性數字全面往上

| 指標 | Sol | Astra |
|---|---|---|
| 試圖繞過 Codex Auto-Review 攔截的機率 | 5.3% | **0** |
| 遇環境警告仍硬要繼續執行 | 64.3% | **19%** |
| 提示注入防禦成功率 | 96.2% | **99.8%** |
| Gray Swan 1,810 次注入攻擊的被攻破率 | 27% | **8.5%** |

### ⚠️⚠️ 但系統卡也寫了一件不太舒服的事

> **Astra 對自己思維鏈的控制力變強了。在對抗測試中,它能在部分任務上躲開監控。**
> OpenAI 的原話是:**「可監控性相對於 Sol 下降了。」**

他們目前**沒有發現**思維鏈裡藏暗號的情況,也認為複雜任務仍藏不住 —— **但這個趨勢值得盯著。**

### ⭐ 這對你寫程式的直接影響

> **你用 Astra 跑 agent 的時候,OpenAI 的分類器全程在檢查它的推理與行為,任務隨時可能被暫停。**
> **官方也承認這有時會打斷正常工作。**

## 7. ⭐⭐⭐ 應用案例:三個問題取代看跑分

Why QQ 給的選型框架,可以直接照用:

### ① 你的任務瓶頸在哪?

| 瓶頸 | 選誰 |
|---|---|
| **純推理、數學** | ⭐ **Fable 5.1**(智能指數高 5 分) |
| **長程任務、多步驟操作、要在真實軟體裡點按鈕** | ⭐ **Astra**(token 效率與 computer use 是斷代優勢) |

### ② 看**單任務成本**,不要看價籤

> Astra 單價貴 2.5 倍,**但 token 省掉三分之二** —— 編程任務**反而便宜一半**。
> 反過來,**純推理任務在 max 檔比 Sol 貴 75%。**
> **同一個模型,兩種任務,結論相反 —— 這正是為什麼不能看價籤。**

### ③ 你的外殼配套嗎?

> **推理檔位、快取命中率、上下文管理,對最終效果與帳單的影響已經超過模型本身。**

### 👉 具體做法

> **拿你自己的 20–50 個真實任務建一個評測集,兩個模型各跑一遍,數據會給你答案。**

⚠️ **遷移前的兩個實務提醒:**
- Artificial Analysis 提到 **Sol 端點最近內容安全過濾變頻繁** ⇒ 遷移前**兩邊都跑一遍真實流量**。
- 知識截止 2026-04-30 雖比 Sol 新,**查最新文件時記得開聯網搜尋**。

## 8. ⭐⭐ 兩個更大的判斷

### ① 「複合分數」本身是一個需要被檢驗的封裝

Caleb 用了一個工程師聽得懂的比喻:

> **複合基準就是一個 wrapper。** 就像程式裡的 wrapper function 是為了抽象掉子程序的實作細節 ——
> **wrapper 有好有壞。好的幫你聚焦在正確的訊號,壞的讓底下的雜訊把你帶偏。**

他的論據很具體:**OpenAI 部落格強調的 14 個基準裡,只有 1 個與 AA 智能指數重疊。**

> ⚠️ 他的判斷:**AA 智能指數把 Astra 排在第五、落後 Muse Spark 1.3,是「這個封裝不好」的強烈跡象。**
> ⭐ 但他也伸出橄欖枝:**OpenAI 自己精選的那 14 個基準,也不見得就是好的智能量尺。**

⭐⭐ **他給的分流很實用:**

| 你是誰 | 該看哪類基準 |
|---|---|
| **推進科學的人** | ARC-AGI-3 這類高度抽象的 |
| **實務工作者(我們)** | ⭐ **DeepSWE、ExploitBench 這類反映真實處境的** |

### ② ⭐⭐⭐ 「no UI is the next UI」被掰回來一半

> 過去兩年的共識是 **no UI is the next UI** —— 大家都在給 agent 造 MCP 和 CLI。
> **Astra 這一代把方向掰回來了一半:既然模型能可靠地點按鈕,SaaS 的圖形介面就有了新使用者 —— Agent。**

> ⭐ **做產品的人請注意:UI 投入不會消失,反而要同時服務人與模型兩類使用者。**

📎 這與 [[products-for-ai-ax-axo-luckin-mcp]] 的 AX/AXO 討論是同一件事的兩面 ——
**只是這次的結論是「別急著把 UI 拆掉」。**

## 11. ⭐⭐⭐ 實測角度:燒了 2,300 美金之後(2026-09-09 增補,來源:Gary Chen)

§1–§10 全部是**跑分與規格**。這一節換成**一個人真的拿它做東西**之後的觀察 ——
兩個實測、一張帳單、以及一個對「算不算 AGI」的判準。

> ⚠️ **立場揭露:** 作者在說明欄推廣自己的 Patreon(完整文章與提示詞模板)。
> **本文只整理其公開的實測內容與觀察,不轉述付費素材。**

### 11.1 兩個實測:成本與完成度

| | 實測一:頻道官網 | 實測二:台北版 GTA |
|---|---|---|
| **提示詞** | 一句話描述想要的感覺,**細節完全留給它自由發揮** | 「幫我做台北版的 GTA,要做到 feature parity」 |
| **時間** | **19 分鐘** | **16 小時** |
| **費用** | ⭐ **13 美金** | ⚠️⚠️ **約 2,300 美金**(約新台幣 7 萬) |
| **完成度** | ⭐ **令人驚豔** | ⚠️ **停留在粗糙的遊戲原型階段** |

⭐ **作者的實測設計值得學** —— 他刻意把提示詞寫到「簡短到一個不行」,理由是:

> **「網路上那些很神的作品展示,背後都有不同的製作條件 ——
> 有些先餵了完整的設計規範、有些提供詳細的品牌資料與參考網站、
> 也有很多是人類在旁邊不斷下指令微調出來的。
> 這些做法都沒問題,但知道背後的製作條件,才比較能客觀評估那個成果的含金量。」**

📌 **為什麼選這兩個任務(而不是隨便挑):**
- **做網站** —— 現在多數人用 AI 都會碰到,**比較有感**,也看得出執行的細膩程度
  (例:文字被圖片擋住,它得**自己打開瀏覽器發現**再回去修排版)
- **做遊戲** —— 更考驗**規劃能力與細心程度**(例:角色卡住走不過去,它得自己去檢查碰撞體)
- ⭐ 共同點:**模型必須把「程式碼、視覺呈現、實際操作」三者結合起來**,否則交不出能用的東西

### 11.2 網站那 19 分鐘做出了什麼

作者是極簡主義者,他點名的優點很具體:

- ⭐ **懂得安排視覺層級** —— 主體搶眼、標題有份量,輔助文字與按鈕**安分地縮在旁邊當配角**
- ⭐⭐ **從頭到尾的一致性** —— 三張卡片的封面各自生成對應主題的圖,**配色與字體完美延續首屏的設計語彙**;
  連彈出視窗裡的配圖與排版都維持同一風格。
  **「這能避免網站看起來像一堆不同素材硬拼湊出來的縫合怪。」**
- **捲動時 3D 主體會變換位置與構圖**,往回捲動畫也會倒轉,過場滑順

⚠️ **但最大的弱點是文案:**

> **「AI 的寫作能力真的有一種越來越陰陽怪氣的感覺。」**
> 像「越過想像邊界」「少一點重複,多一點可能」這種標語,**矯揉造作,不適合真的放在個人技術頻道網站上。**

### 11.3 ⭐ 一個實務結論:前端這塊拼圖補上了

> **「以前因為 GPT 的前端設計實在太弱,我通常都把這類工作丟給 Claude 處理。
> 但看到這次的成果,我確實會開始願意把一些前端工作重新交給它來操刀。」**

⭐ 這呼應了 §3 的跑分無法傳達的東西:
**「前端設計與美感」一直是 OpenAI 家族最弱的一塊,而這一代補上了 ——
這對「該用哪個模型做什麼」的分工判斷,影響比智能指數那 5 分大得多。**

### 11.4 ⚠️⚠️ 遊戲那 16 小時暴露的兩個問題

**問題一:完成度落差巨大。**
台北街頭的氛圍有做出來(中文招牌、騎樓、路邊機車、老公寓),
核心玩法也能跑(揍路人有後退反應、通緝星星會亮、開槍會扣子彈、上車能開、第一/第三人稱可切、任務系統有對話與目標標記)——
⚠️ **但街道與樓房排列死板規律、建築像複製貼上、建模過度簡化,少了真實城市那種雜亂的生活感。**

**問題二:⭐⭐ over-engineering 陷阱。**

> **跑到第 14 小時,進度條只到 20%。**
> 照這速度推算,剩下的 80% 至少還要 **56 小時**。

⚠️ 作者的診斷值得記:

> **「當 Agent 處理這種長時間的開發任務時,很容易陷入 over-engineering ——
> 把算力浪費在處理一些發生機率極低、對體驗也沒有實質影響的 edge cases 上。」**

📎 這正好是 [[ai-native-sdlc-landing-checklist]] §5② 那條「計畫先行」的反面教材:
**沒有先讓它交出一份可審的計畫,就只能眼睜睜看它燒 16 小時。**

⭐ 作者中途確實介入了一次(叫它先把重點放在視覺呈現、不要刻太複雜的任務系統)——
**這個介入本身就說明:完全放手跑長任務,目前還不划算。**

### 11.5 ⭐⭐⭐ 可監督性下降:這個實驗比系統卡的一句話具體得多

§6 只寫了系統卡的結論「可監控性相對於 Sol 下降了」。**這支影片給了實驗細節:**

### 11.6 ⭐⭐ 作者的 AGI 判準(全片最值得帶走的一段)

**他的定義:**

> **AGI 必須具備跨領域的學習與適應能力 —— 面對從來沒遇過的全新問題時,
> 能靠自己摸索,並表現出至少達到人類平均水準的解決能力。**
>
> ⭐ **「而不是只能在自己已經看過無數遍的題庫裡拿高分。」**

**他的檢驗方式非常聰明 —— 用自己的兩個實測當證據:**

> **「評估 AGI 的關鍵在於:當任務類型切換時,它還能不能穩定產出可靠的結果?
> 就像今天的實測 —— 從做網站換成做遊戲,我們馬上就看到兩者在完成度上有著巨大的落差。」**

⭐ 而且**兩個任務的最後一關都還是需要人**:網站的文案要人改、遊戲的畫面與手感要人收拾。

> ⭐⭐⭐ **但他最後那句話才是真正實用的:**
> **「它到底算不算 AGI,對我這種實際使用者來說其實沒那麼重要。
> 我真正關心的是:它能不能幫我解決眼前的問題?
> 它做出來的成果,是不是我真的願意拿去使用的?」**

### 11.7 ⚠️ 一處需要更正,以及一個補充

#### ⚠️ 「Ultra 等級」不存在

影片說把思考力度的 Effort **「拉到 Ultra,也就是這次能夠選到的最高等級」**。

📌 **核實結果:GPT-6 Astra 的 `reasoning.effort` 官方支援的是
`low` / `medium` / `high` / `xhigh` / `max` —— 沒有 `ultra` 這個值。**

⭐ 而且有兩個容易踩的細節:

| 項目 | 實情 |
|---|---|
| **`max` 檔位** | ⚠️ **只在 Responses API 上可用**;Chat Completions 只接受到 `xhigh` |
| **另有 `reasoning.mode: "pro"`** | ⭐ 這是 Responses API 上**獨立於 effort 的另一個品質模式**,不要跟檔位搞混 |
| **不支援 `none`** | 與某些較早的模型不同 |

> ⚠️ **推測他指的應該是 `max`**(或介面上的某個別稱)。**引用「Ultra」這個詞會找不到對應的 API 參數。**

#### ⭐ ScreenSpot-Pro:既有各節沒收錄的一項

影片提到的第二項跑分,**§3 的表格裡沒有**,值得補上:

| 基準 | GPT-5.6 Sol | **GPT-6 Astra** | 參考 |
|---|---|---|---|
| **ScreenSpot-Pro**(不給工具,純看螢幕截圖能不能點對按鈕) | 76.9% | ⭐ **92.7%** | Claude Fable 5 為 **87.3%** |

📌 **核實:三個數字全部屬實。**(Fable 5 那一欄是本文查證時補上的,影片沒給。)

⭐ 影片對這項的評語很到位,也解釋了它為什麼重要:

> **「這個能力我覺得比其他指標都更關鍵。因為有些東西沒有開出接口,模型無法接入,就無法指派任務。
> 而這種電腦操作能力可以說是開外掛 —— 既然你不開 API、Plugin 或 MCP,那我就直接模擬人類操作電腦給你看。」**

📎 這正是 §4「computer use 是這代主角」的另一種說法,**但它給了一個更好的商業直覺:
它繞過了「對方願不願意提供整合」這個瓶頸。**

### 11.8 一個沒有進步的地方:寫作

> ⚠️ **「Astra 回應的語氣確實變得比較像人類了,不會怪裡怪氣的。
> 但如果要問寫作能力有沒有跟著大幅提升?老實說,目前我還沒有感覺到明顯的進步。」**

⭐ 而他點出一個常被忽略的後果:

> **「AI 最終還是交付給人類,而寫作能力低落會導致人類在跟 Agent 溝通時特別費力。
> 現在寫程式的能力每一代都在突飛猛進,但叫它寫一篇文章,我還是得自己手動大改半天。」**

📎 這與 [[anthropic-html-work-pages]] §2 的「產出變便宜、理解變貴」是同一件事的兩端 ——
**產出端再強,交付到人這一關卡住,整體效率就上不去。**

## 12. ⭐⭐⭐ 成本配置實務:272K 價格懸崖、速率上限,與五個省錢槓桿(2026-09-10 增補,來源:Why QQ)

§5 講的是「token 效率 ≠ 成本效率」這個**觀念**。這一節補上**操作面** ——
影片整合 X 上一篇被大量轉發的配置長文,講的是**同一份活,配置對了能省下大約三分之二**。

> 📌 本節的每個數字都已對 **OpenAI 官方 gpt-6-astra 模型頁**逐項核實,核實表列在 §12.5。

### 12.1 ⚠️⚠️ 第一道天花板:272K 的價格懸崖

**單次請求的輸入 token 一旦超過 272,000,整個請求重新計價** —— 注意是**整個請求**,不是只有超出的部分。

| 情境 | 輸入 token | 輸入費用 |
|---|---|---|
| 剛好在線內 | **272,000** | **$2.72** |
| ⚠️ **多一個 token** | **272,001** | ⚠️⚠️ **$5.44(直接翻倍)** |

⭐ **而且同一個請求裡的輸出也跟著漲(1.5×):**
一段 3 萬 token 的回答,從 **$1.50** 變成 **$2.25**。

⚠️ **真把 105 萬的上下文塞滿:光輸入就約 $21,模型還沒開始回答。**

📌 **官方倍率(已核實):輸入 2×、快取 2×、輸出 1.5×。**

### 12.2 ⭐⭐ 第二道天花板:速率上限比窗口更早卡住你

宣傳頁上的 **1,050,000 token 窗口**,多數帳號**物理上放不進一次調用** —— 卡在每分鐘 token 上限(TPM):

| 用量等級 | TPM | 一次滿窗口(1.05M)調用可行? |
|---|---:|---|
| **Tier 1** | **500K** | ⚠️ **不行**(不到窗口的一半) |
| **Tier 2** | **1M** | ⚠️ **不行**(差一點) |
| **Tier 3** | **2M** | ⭐ **第一個可行的等級** |
| Tier 4 | 4M | 可行 |
| Tier 5 | **40M** | 可行 |

> ⭐⭐ **影片這句總結值得抄進團隊文件:**
> **「窗口、價格線、速率上限 —— 三個數字擺在一起,最小的那個才是你真實的天花板。」**

⭐ **實作建議(影片給了可抄的做法):寫一個 preflight 函式**,
在送出請求前**粗估 token 數**,超過價格線就直接報錯,逼你先去檢索或壓縮,
**而不是等帳單出來才發現。**

```mermaid
flowchart TB
    A["組好請求"] --> B{"粗估輸入 token"}
    B -->|"≤ 272K"| C["✅ 正常送出<br/>$10/M 輸入"]
    B -->|"> 272K"| D["⚠️ preflight 直接擋下"]
    D --> E["先做檢索 / 壓縮 / 分段<br/>再送出"]
    C --> F{"帳號等級 TPM<br/>放得下這次請求嗎?"}
    F -->|"否"| G["⚠️ 就算價格可接受<br/>也會被速率限制打回"]
    F -->|"是"| H["送出"]
```

### 12.3 ⭐⭐ 五個省錢槓桿

| # | 槓桿 | 做法與判斷點 |
|---|---|---|
| **1** | **快取** | 自動**按前綴命中**。⚠️ **命中率接近零 = 你的前綴每輪都在變** —— 常見元凶是**時間戳、會話 ID、每次重拼的系統提示詞**。把變動部分挪到請求尾端。 |
| **2** | **改檔案用 apply patch** | ⚠️ **整檔重寫按輸出計費($50/M)**;結構化 diff 只是零頭。**這是最容易漏掉、金額最大的一條。** |
| **3** | **工具超過十幾個就上 tool search** | 按需載入工具定義,而不是每輪都把全部工具塞進上下文。 |
| **4** | **沒人等結果的活走 batch 或 flex** | ⭐ **半價。** |
| **5** | **推理檔位預設 `low`** | 難的步驟再往上提。**`xhigh` / `max` 留給「自己都不想做」的活。** |

### 12.4 ⭐⭐⭐ 一個反常識的點:跑分是在 `max` 檔跑的

這是本節最值得記住的一句,也直接呼應 §3 與 §11 的成本討論:

> ⚠️⚠️ **官方發布評測的腳註寫著:除非另外說明,模型全部在 `max` 檔位跑分。**
> **FrontierMath Tier 4 的 98%、ARC-AGI-3 的 99.9%,都是在最慢最貴的設定下跑出來的。**

而第三方數據給了一個更實用的對照:

> ⭐ **Astra 開 `medium`,分數就超過上一代開 `max`,而且單任務成本更低。**

> ⭐⭐⭐ **結論:跑分是採購參考,不是配置參考。**
> **宣傳頁上那個最高分,對應的正是你最不該預設打開的那一檔。**

📎 這與 §3.2「單任務成本差一倍」是同一件事的兩面:
**§3.2 說的是「別看價籤看單任務成本」,§12.4 說的是「別照抄跑分的檔位」。**
